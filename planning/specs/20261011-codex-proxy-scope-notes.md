# Codex 代理集成讨论断点

日期：2026-10-11。用户要求先记录，晚上继续讨论。本轮不开发、不运行 CPA、不安装依赖、不登录或调用模型。

## 已表达的方向

- 首版只复用 Codex 代理能力，其他供应商代理以后再考虑。
- 用户重点担心软件越来越笨重、安装包越来越大。
- 倾向将所需代理随 Droid Switch 安装包集成，用户无需另外安装 CPA 或手动开终端。
- 这里的集成可以是随包附带受管后台进程，不要求把 Go 代码改写为 Rust。

## 当前构思（尚未最终定案）

1. 开发验证阶段先用固定版本完整 CLIProxyAPI，仅测试 Codex 登录、续期、模型目录、流式响应和 Droid 多轮工具调用。验证用完整包不等于决定交付完整包。
2. 交付前评估 Codex 专用精简构建：保留授权、令牌刷新、模型列表、必要请求/流式转换及最小管理接口；检查能否移除其他供应商、管理网页、插件和无关模块。
3. 产品界面由 Droid Switch 提供，不再附加重复管理网页。仅启用 Codex 代理时启动进程，停止后释放资源。
4. 以后新增代理按独立模块/可选组件设计；是否按需下载，留待分发方式、更新和离线安装需求明确后讨论。
5. 对比四项真实指标：安装包大小、安装后磁盘占用、空闲内存、启动耗时。另记录请求期间额外内存、并发表现及维护成本，不能只看文件大小。

## 明确的技术边界

- UI 隐藏其他供应商不等于裁掉其代码；完整 CPA 二进制仍可能包含这些功能。
- Codex 授权、传输与协议转换可能依赖共享模块，是否能干净裁剪、裁剪能省多少，需要构建与测量。
- 精简分支会带来跟进上游修复、跨平台构建与签名的持续工作；不能把减小体积视为零维护成本。
- 当前还没有 CPA 平台产物体积/内存基线，没有运行兼容测试，不能承诺大小或确定工期。
- 新授权流程与旧 Codex OAuth 路径的区别见前期源码调研；本笔记不改变其未验证状态。

## 晚上继续讨论的问题

- 可接受的安装包增量与空闲内存范围，用来决定裁剪是否值得。
- 选择完整核心但只启用 Codex、维护 Codex 精简构建，还是单独可选组件。
- 首版随安装包带齐，还是首次启用时再下载代理组件。
- 关窗口是否托盘常驻；完全退出时停止代理的交互。
- 验证通过后，再细化版本固定、跨平台签名、更新回退与上游维护策略。
